# Разработка новых версий для site с использованием отдельного репозитория site_dev!


Есть репозиторий с первой версией продукта site и его папка site на ПК.
Паркуем site - оставляем активной только одну версию на gitHub.
Создаём новый проект: 
    открываем в редакторе кода родительскую папку для site_dev,
    делаем клон первой версии site в папку site_dev: 
         git clone <ссылка-на-репозиторий-site> site_dev
    заходим в созданную папку:
        cd site_dev
    отключаем клон от site:
        git remote remove origin
    обновляем все зависимости:
        npm install
    исправляем ошибки зависимостей:
        npm audit fix
    создаём новый закрытый репозиторий site_dev,
    подключаем клон из папки site_dev к новому репозиторию site_dev: 
        git remote add origin <ссылка-на-новый-репозиторий-site_dev>  
        git branch -M main
        git push -u origin main
Меняем все пути в новом проекте site_dev в служебных файлах с /site/ на /site_dev/ - глобальный поиск и замена (Ctrl + Shift + H / Cmd + Shift + H) по строке '/site/' на '/site_dev/' (и аналогично для переменных окружения или конфигураций роутера). 

Получаем полностью независимый от site закрытый проект для разработки. Если нужен открытый для тестирования, то смотри ниже!

Проводим разработку новой версии. Обращаем основное внимание на IndexedDB - если вносим изменения в структуру базы данных, то обязательно меняем версию базы данных. При этом оставляем название базы данных старой. В папке src прменяется универсальный сокращённый путь '$lib/...' - он будет безопасно использоваться и в новом и в старом репозитории, потому что они идентичны. Каждое улучшение делаем отдельной веткой с последующим слиянием в site_dev.
Репозиторий site_dev делаем открытым для разных устройств: 
    переключите видимость репозитория site_dev в настройках на Public (публичный)
 и 
    включите GitHub Pages в разделе Settings -> Pages -> Source: GitHub Actions:
        Перейдите во вкладку Settings (Настройки) в верхней панели репозитория.
        В левом боковом меню найдите раздел Code and automation -> Pages.
        В блоке Build and deployment найдите параметр Source.
        Измените значение с «Deploy from a branch» на GitHub Actions.
        Сохраните изменения (если кнопка сохранения появится).
        После этого запустите деплой (или сделайте пустой коммит / повторный push) в репозиторий site_dev — ошибка пропадет, и GitHub Actions успешно опубликует превью-версию.
Тестируем новую версию.
Когда вся разработка завершена обновляем основной проект до новой версии: 
    открываем Проводник и копируем: 
        содержимое папки site_dev/src в папку site/src (с заменой), 
        копируем обновленные файлы из site_dev/static (или public) в site/static, ТОЛЬКО если в процессе разработки добавлялись новые медиафайлы или ассеты. Из папки site/static копируем ТОЛЬКО новые файлы! 
        Служебные конфиги (vite.config.js, .git, и т.д.) в корне папок НЕ КОПИРОВАТЬ, так как в site они уже правильно настроены под основной домен.
        Если используются новые npm-пакеты (зависимости package.json) при разработке новой версии продукта, то копируем и  package.json.
После копирования, открываем папку site в редакторе кода: 
    ПРОВЕРИТЬ ЧТОБ В ПАПКЕ src/ не было упоминаний о /site_dev/ - при необходимости заменить их руками на /site/
    ЕСЛИ вносились изменения в файл site_dev/static/manifest.json то прописываем путь для site/static/manifest.json! 
    ЕСЛИ БЫЛИ ДОБАВЛЕНЫ НОВЫЕ ПАКЕТЫ (файлы package.json отличаются), то обновляем зависимости, запустить: 
        npm install
    делаем коммит со всеми обновлениями.
Получаем продукт в репозитории site со второй версией.
Для пользователей процесс разработки будет не заметным. Просто произойдёт одно обновление.
Папку и репозиторий  site_dev можем использовать для разработки и тестирования следующей версии продукта и так по циклу.

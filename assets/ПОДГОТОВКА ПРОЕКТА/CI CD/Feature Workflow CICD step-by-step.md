Шпаргалка: Полный цикл разработки (Feature Workflow):

Чистый main -> Новая ветка -> Работа -> Push -> Слияние на GitHub -> Удаление ветки.

Этот алгоритм описывает путь от идеи новой функции до 
её появления на живом сайте с использованием GitHub Actions (CI/CD).

Этап 1: Подготовка и создание ветки

Никогда не делайте правки сразу в main, если проект уже задеплоен.

    1. Обновите локальный main:
        git checkout main
        git pull origin main

    2. Создайте ветку для новой задачи (например, feat-pwa):
        git checkout -b feat-pwa

Этап 2: Разработка и локальная проверка

    1. Пишите код, добавляйте файлы (static/sw.js, manifest и т.д.).

    2. Проверьте сборку локально:
        npm run build
        npm run preview

Если в preview всё работает (PWA устанавливается, пути верные) — можно отправлять.


Этап 2,5: Service Worker (PWA) при деплое.автоматизирован
    
    1. Проверь список файлов в addAll. Если там есть старые пути, которых больше нет — удали их.
    2. Измени версию кэша (например, с v1 на v2). Это заставит браузер понять, что старые данные пора выкинуть.
    3. console.log -  не удаляются автоматически при сборке! 
 

Этап 3: Пуш и Pull Request (PR)

    1. Добавьте изменения в индекс:
        git add .

    2. Сделайте коммит:
        git commit -m "feat: добавлена поддержка PWA и сервисного рабочего"

    3. Отправьте ветку на GitHub:
        git push origin feat-pwa

1. 2. 3. - можно сделать через боковое меню!
______________________________________________________________________  
_________________________________tiri__________________________________ nextUpdate2
______________________________________________________________________   
_______________________________amoca________________________________ nextFeature2

    4. Создайте Pull Request: Зайдите в репозиторий на GitHub, нажмите "Compare & pull request". 
    Проверьте изменения и нажмите "Create pull request".

Этап 4: CI/CD и Слияние (Merge)
    
    1. GitHub Actions: После создания PR или пуша в main, во вкладке Actions запустится ваш воркфлоу (deploy.yml).
        ◦ Дождитесь зеленой галочки.
    
    2. Слияние: Если тесты/сборка прошли успешно, нажмите "Merge pull request" на странице PR.
    
    3. Удаление ветки на GitHub: После мерджа GitHub предложит кнопку "Delete branch" — нажмите её.

Этап 5: Финальная очистка локально

Теперь нужно привести локальный компьютер в соответствие с тем, что на сервере.

    1. Вернитесь в main: 
        git checkout main

    2. Заберите изменения из облака: 
        git pull origin main

    3. Удалите локальную временную ветку: 
        git branch -d nextUpdate1

(Если Git ругается, что ветка не объединена, но вы уверены в успехе мерджа — используйте -D).

    4. Синхронизируйте список всех веток (удалите "призраки" удаленных веток):
        git fetch --prune
 
    5. Создайте НОВУЮ ветку под НОВУЮ задачу. Это самый важный момент. Каждая фича — новая ветка.
        git checkout -b nextUpdate2


Полезные команды "на всякий случай"

    • Отмена последнего коммита (с сохранением кода): 
            git reset --soft HEAD~1
    • Просмотр статуса: 
            git status
    • Просмотр веток: 
            git branch -a
    • Перейти в  ветку feat-new-logic: 
            git branch feat-new-logic

    • Перейти в ветку и удалить её
    1. git checkout main (убедиться, что вы не в удаляемой ветке)
    2. git branch -d triton (удалить локальную копию)
    3. git push origin --delete triton (удалить копию на GitHub)



    • Если забыли .nojekyll: Убедитесь, что в static/ лежит пустой файл .nojekyll, иначе GitHub Pages сломает пути SvelteKit.
    • Зачем нужен .nojekyll?: GitHub Pages по умолчанию использует движок Jekyll, который игнорирует любые папки, начинающиеся с нижнего подчеркивания (например, _app в SvelteKit). Файл .nojekyll отключает этот движок. Если ваш скрипт деплоя в GitHub Actions (например, JamesIves/github-pages-deploy-action) имеет параметр dotfiles: true, он может создавать этот файл автоматически. Однако лучше иметь его в static/, чтобы гарантировать работоспособность PWA и загрузку стилей. 



ВОССТАНОВИТЬ УДАЛЁННУЮ ВЕТКУ

Удалил ветку в которой не получилось реализовать страницу проекта.
Но в удалённой ветке были несколько существенных дополнений для стилей и разметки.
Вопрос: можно восстановить удалённую и на ПК и в репозитории ветку?

Да, восстановить ветку можно, даже если вы удалили её и на ПК, и на GitHub!
Пока вы работали в этой ветке на компьютере, Git сохранял следы ваших действий во внутреннем журнале, который называется reflog. Удаление ветки просто стирает «ярлык», но сами коммиты с вашими стилями и разметкой ещё какое-то время живут в памяти Git.

Вот пошаговый план спасения ваших наработок:

Шаг 1: Ищем следы удаленной ветки
В терминале IDE введите команду, которая покажет историю всех перемещений и коммитов (даже удаленных):

Bash
git reflog

Вы увидите список строк, похожих на этот:

Plaintext
a1b2c3d HEAD@{0}: checkout: moving from triton to main
e5f6g7h HEAD@{1}: commit: feat: добавлен классный дизайн и новые стили
j9k8l7m HEAD@{2}: commit: fix: разметка шапки сайта


Шаг 2: Находим нужный коммит
Листайте этот список стрелочками вверх/вниз. Ищите коммит, в котором вы делали те самые существенные дополнения к стилям или разметке (в примере выше это коммит e5f6g7h с текстом "feat: добавлен классный дизайн...").
Вам нужен хэш коммита — это комбинация из 7 символов (буквы и цифры) в самом начале строки.


Шаг 3: Возрождаем ветку из пепла
Когда хэш найден (допустим, это e5f6g7h), нажмите q, чтобы выйти из режима просмотра reflog, и введите команду:
Bash

git checkout -b br-restored 7a6e377 


(Вместо e5f6g7h подставьте свой хэш, а имя ветки triton-restored можно сделать любым).
Что произошло: Git взял состояние вашего кода на момент того самого коммита и создал из него абсолютно новую рабочую ветку!
Шаг 4: Забираем только стили (Альтернативный вариант)
Если вы не хотите восстанавливать всю ветку целиком (чтобы опять не тащить туда неудавшийся функционал страницы), а хотите забрать только стили в текущую чистую ветку main:
    1. Перейдите в main: git checkout main
    2. Перенесите в неё конкретный коммит со стилями по его хэшу:
       Bash
       git cherry-pick e5f6g7h
Git возьмет изменения только из этого коммита и аккуратно применит их к вашей главной ветке.
Шаг 5: Возвращаем ветку на GitHub (если нужно)
Как только локально в IDE всё восстановилось, просто отправьте ветку обратно в облако:
Bash
git push origin triton-restored
Главное правило: Не делайте сейчас git gc (очистку мусора) в терминале. Пока вы этого не сделали, ваши удаленные коммиты будут гарантированно храниться на ПК еще около двух недель. Всё поправимо!
